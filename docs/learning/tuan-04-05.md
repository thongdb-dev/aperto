## Tuần 4

### Buổi 1–2 (~6h): CRUD profile, packages, booking policies

**Học (1h):** ôn lại Mongoose ref + populate; class-validator nâng cao: `@ValidateNested`, `@Type`, validate mảng object (cần cho `milestones` trong booking_policies).

**Làm:**

- [ ] Schema `photographer_profiles`, `packages`, `booking_policies` theo [docs/04-data-model.md](../04-data-model.md) — chú ý `verification_status` mặc định `unverified`, `trust_score`/`trust_level` để sẵn field (M7 mới tính)
- [ ] CRUD endpoints: profile của chính mình (`PATCH /photographers/me/profile`), packages (`POST/PATCH/DELETE /photographers/me/packages`), policy tương tự
- [ ] Phân quyền bằng `RolesGuard` từ M1: chỉ photographer sửa được của mình — viết logic "ownership check" (photographer A không sửa được package của B)
- [ ] Endpoint công khai `GET /photographers/:id` trả profile + packages đang active — **không cần** đăng nhập

**Tự vấn:** DTO cho create và update khác nhau thế nào (`PartialType` từ `@nestjs/mapped-types`)? Ownership check nên đặt ở Guard hay Service? (thường Service, vì cần query DB).

### Buổi 3 (~3h): Presigned URL — lý thuyết + setup storage

**Học (1.5h):** đọc về presigned URL (AWS docs hoặc Cloudflare R2 docs). Trả lời được trước khi code:

- Tại sao FE upload thẳng lên R2 thay vì gửi file qua API? (API không phải buffer file lớn → không nghẽn event loop, không tốn băng thông server)
- Chữ ký giới hạn được gì? (bucket/key, content-type, content-length, thời hạn)
- Presigned **upload** (PUT) khác signed **download** (GET có expiry) thế nào — M5 sẽ dùng cái sau

**Làm (1.5h):**

- [ ] Chọn 1: đăng ký Cloudflare R2 free tier, hoặc thêm MinIO vào `docker-compose.yml` (khuyên MinIO để dev offline được; R2 để dành lúc deploy)
- [ ] Cài `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`, viết `StorageModule` (provider pattern giống `RedisModule` Tuần 1)
- [ ] Upload thử 1 file bằng script trước khi làm API

### Buổi 4 (~3h): API cấp presigned URL + schema photos

**Làm:**

- [ ] Schema `photos`: `project_id` (tạm nullable — portfolio chưa gắn project), `type` (`raw`/`edited`/`moodboard`), `url`, `thumbnail_url`, `uploaded_by`
- [ ] `POST /media/presign`: nhận filename + content-type + size → validate (chỉ image/*, size ≤ giới hạn) → trả presigned PUT URL + key
- [ ] `POST /media/confirm`: FE gọi sau khi upload xong → tạo document `photos`
- [ ] Field tổng dung lượng đã dùng (phục vụ Q6 5GB/project sau này) — chỉ cộng dồn, chưa chặn

**Tự vấn:** nếu FE gọi presign nhưng không bao giờ upload, hệ thống có rác gì không? Nếu upload xong nhưng không gọi confirm thì sao? (ghi nhận vấn đề orphan file vào Nhật ký — chưa cần giải, M8 backlog).

## Tuần 5

### Buổi 5 (~3h): BullMQ worker sinh thumbnail

**Học (1h):** [docs.bullmq.io](https://docs.bullmq.io) — Queue, Worker, retry với backoff. Khi nào cần queue thay vì xử lý sync: việc chậm (resize ảnh), việc được phép fail-retry, việc không cần kết quả ngay trong response.

**Làm (2h):**

- [ ] Queue `media` dùng Redis sẵn có; sau `confirm` → add job `generate-thumbnail`
- [ ] Worker: tải ảnh từ storage → `sharp().resize(400).webp()` → upload thumbnail → cập nhật `thumbnail_url`
- [ ] Cấu hình retry 3 lần, exponential backoff; job fail hết retry thì log lại

**✅ Kiểm chứng giữa module:** trả lời bằng lời — worker chết giữa chừng thì job có mất không? (job ở trạng thái active sẽ được retry khi worker sống lại / stalled check). Job chạy 2 lần thì có tạo 2 thumbnail khác nhau không? (idempotency: cùng key đích → ghi đè, vô hại — đây là ví dụ idempotency đầu tiên, M6 sẽ gặp lại với webhook).

### Buổi 6–7 (~6h): FE — trang profile công khai + upload nhiều ảnh

**Làm:**

- [ ] Trang `/photographers/[id]`: profile + portfolio grid, lazy-load ảnh (next/image), lightbox khi click
- [ ] Form upload nhiều ảnh: chọn N file → gọi presign song song → upload trực tiếp lên storage với **progress bar từng file** (axios `onUploadProgress`) → confirm từng file
- [ ] Polling hoặc refetch bằng React Query để thấy `thumbnail_url` xuất hiện dần khi worker xử lý xong
- [ ] Trang quản lý portfolio của photographer: xoá ảnh, sắp xếp

### Buổi 8 (~2h): Tổng kiểm chứng

- [ ] **Upload 50 ảnh một lúc**: API chỉ cấp chữ ký (nhanh), upload đi thẳng storage, thumbnail sinh dần bất đồng bộ, UI cập nhật khi xong. Quan sát queue bằng `redis-cli` hoặc Bull Board (cài thử — đáng giá 15 phút)
- [ ] Kill worker giữa chừng khi đang xử lý 50 job → bật lại → job tiếp tục, không mất
- [ ] Giải thích được idempotency của job bằng lời
- [ ] Nhật ký: chọn R2 hay MinIO, lý do; vấn đề orphan file ghi nhận thế nào
