## Workflow nhánh cho M1

`develop` là integration branch cho từng milestone; `main` chỉ nhận merge khi cả milestone hoàn tất (PR `develop → main`). Vì các phần của Auth phụ thuộc tuần tự (login cần schema user, refresh cần login, FE cần refresh...), nhánh tạo **nối tiếp nhau** từ `develop` đã cập nhật — không tách song song từ cùng một điểm.

| Nhánh | Nội dung | Buổi |
|---|---|---|
| `feat/m1-users-register` | Schema `users`, hash bcrypt, `POST /auth/register` | 1 |
| `feat/m1-jwt-login` | Login, access token, Passport JWT strategy, `JwtAuthGuard` | 2 |
| `feat/m1-roles-guard` | `@CurrentUser()`, `@Roles()`, `RolesGuard` | 3 |
| `feat/m1-refresh-rotation` | Refresh token + rotation + revoke qua Redis | 4 |
| `feat/m1-otp-verify` | OTP email xác thực | 5 |
| `feat/m1-web-auth` | FE form đăng ký/đăng nhập + axios interceptor tự refresh | 6–7 |

Buổi 8 (unit test `AuthService` + kiểm chứng cuối module) không cần nhánh riêng — mỗi nhánh ở trên tự mang theo unit test cho phần mình vừa viết; Buổi 8 chỉ rà lại + bổ sung case còn thiếu, làm trên nhánh cuối (`feat/m1-web-auth`) hoặc tách `chore/m1-test-coverage` nếu phát sinh nhiều.

Quy trình mỗi nhánh:

```bash
git checkout develop && git pull
git checkout -b feat/m1-jwt-login
# ... code + test cho buổi đó ...
git push -u origin feat/m1-jwt-login
gh pr create --base develop --title "M1: JWT login + guard"
# review/merge → quay lại develop, pull mới nhất, tạo nhánh kế tiếp
```

CI ([ci.yml](../../.github/workflows/ci.yml)) chạy trên mọi `pull_request` không giới hạn nhánh đích, nên PR vào `develop` đã được kiểm tra tự động — không cần sửa thêm.

Cuối M1, khi mục ✅ toàn module đạt: một PR `develop → main`, title `"M1: Authentication complete"`.

## Tuần 2

### Buổi 1 (~3h): Mongoose schema + đăng ký

**Học (1h):** Mongoose docs — Schema, Model, `@nestjs/mongoose` (`@Schema()`, `@Prop()`, `SchemaFactory`). bcrypt: salt là gì, cost factor (dùng 10–12), tại sao SHA256 không đủ cho mật khẩu (quá nhanh → brute-force dễ; bcrypt cố tình chậm). Giải thích chi tiết: [tuan-02-mongoose-bcrypt.md](./tuan-02-mongoose-bcrypt.md).

**Làm (2h):**

- [x] Tạo `users` schema theo [docs/04-data-model.md](../04-data-model.md): email/phone unique index, `password_hash`, `role`, `status` (mặc định `pending_verification`)
- [x] `AuthModule` + `POST /auth/register`: DTO với `class-validator` (email hợp lệ, hash bằng `bcrypt.hash(password, 10)`) — lưu ý: `RegisterDto` hiện dùng `MinLength(6)`, khác với ≥8 ký tự ghi trong bài; kiểm tra lại xem đây là quyết định có chủ đích hay sai sót
- [ ] Lưu ý Q7: field `role` nên là **mảng roles** hoặc thiết kế cho phép một user giữ cả 2 vai trò — code đã làm đúng (`roles: string[]` trong [user.schema.ts](../../apps/api/src/users/schemas/user.schema.ts)), nhưng **chưa ghi quyết định vào Nhật ký** ở LEARNING.md (mục Nhật ký vẫn đang trống)

**Tự vấn:** unique index của Mongo khác validate trong DTO thế nào? (index chặn race condition, DTO chỉ chặn input xấu — cần cả hai). Email trùng thì API trả lỗi gì — 409 hay 400?

### Buổi 2 (~3h): JWT login — access token

**Học (1h):** cấu trúc JWT (header.payload.signature), jwt.io để decode thử. Access vs refresh: access ngắn hạn (15') đi kèm mọi request, refresh dài hạn (7 ngày) chỉ dùng để xin access mới. Lưu ở đâu: cookie httpOnly (chống XSS đọc trộm) vs localStorage (đơn giản nhưng XSS đọc được) — chọn 1, ghi trade-off vào Nhật ký. Giải thích chi tiết: [tuan-02-jwt-tokens.md](./tuan-02-jwt-tokens.md).

**Làm (2h):**

- [x] `POST /auth/login`: so mật khẩu bằng `bcrypt.compare`, sai trả 401 với **thông báo chung chung** ("email hoặc mật khẩu sai" — không lộ email tồn tại hay không)
- [x] Ký access token bằng `@nestjs/jwt`, payload tối thiểu: `sub` (user id), `roles`, hết hạn 15 phút
- [x] Passport JWT strategy + `JwtAuthGuard`; endpoint thử `GET /auth/me` trả thông tin user hiện tại

### Buổi 3 (~3h): Guard, decorator, phân quyền

**Học (45'):** NestJS docs — Guards, Custom decorators, `Reflector` + `SetMetadata`. Giải thích chi tiết: [tuan-02-guards-passport.md](./tuan-02-guards-passport.md).

**Làm (2h15'):**

- [x] Custom decorator `@CurrentUser()` lấy user từ `request.user`
- [x] `@Roles('photographer')` + `RolesGuard`: đọc metadata bằng `Reflector`, so với roles trong token (endpoint mẫu: `GET /auth/photographer-only`)
- [ ] Test bằng curl: user chỉ có role customer gọi endpoint photographer → 403 — endpoint đã sẵn sàng để test, nhưng chưa thấy bằng chứng đã chạy thử (script/log)

**Tự vấn:** Guard chạy trước hay sau Pipe/Interceptor? (thứ tự: Middleware → Guard → Interceptor → Pipe → Handler). `JwtAuthGuard` và `RolesGuard` phối hợp thế nào khi gắn cả hai?

### Buổi 4 (~3h): Refresh token + rotation + revoke qua Redis

Phần khó nhất module — làm chậm và vẽ diagram trước khi code.

**Học (45'):** tại sao cần rotation: nếu refresh token bị lộ, rotation làm token cũ vô hiệu ngay lần dùng kế tiếp → phát hiện được trộm. Đọc về "refresh token reuse detection". Giải thích chi tiết: [tuan-02-jwt-tokens.md](./tuan-02-jwt-tokens.md#4-refresh-rotation--reuse-detection).

**Làm (2h15'):**

- [x] Login trả thêm refresh token (7 ngày), lưu **hash** của nó vào Redis với key `refresh:{userId}:{tokenId}`, TTL 7 ngày
- [x] `POST /auth/refresh`: verify refresh token → so với Redis → cấp cặp token **mới**, xoá key cũ (rotation)
- [x] `POST /auth/logout`: xoá refresh token khỏi Redis → token cũ bị từ chối
- [x] Dùng lại refresh token đã rotate → 401 (và cân nhắc: revoke toàn bộ session của user đó) — `AuthService.refresh` đã revoke toàn bộ key `refresh:{userId}:*` khi phát hiện reuse

**✅ Kiểm chứng giữa module:** vẽ sequence diagram luồng refresh **không nhìn tài liệu** — Customer → API → Redis, đủ 3 tình huống: access hết hạn, refresh hợp lệ, refresh đã bị rotate.

### Buổi 5 (~3h): OTP email xác thực

**Học:** Giải thích chi tiết: [tuan-03-otp-axios-interceptor.md](./tuan-03-otp-axios-interceptor.md#phần-a--otp-email-xác-thực).

**Làm:**

- [x] Sinh OTP 6 số khi đăng ký, lưu Redis key `otp:{userId}` TTL 10 phút, giới hạn 5 lần thử (`AuthService.sendOtp` / `verifyOtp`) — sửa thêm bug cũ: `attempts` trước đây không bao giờ tăng (thiếu `INCR`) nên giới hạn 5 lần thử chưa từng có tác dụng; đã đổi sang `redis.incr(attemptsKey)` mỗi lần sai
- [x] Gửi email qua Resend hoặc Mailtrap (dev); `POST /auth/verify-otp` → chuyển `status` sang `active` — `register()` giờ tự gọi `sendOtp()` ngay sau khi tạo user; endpoint `POST /auth/verify-otp` (`VerifyOtpDto`) đã nối vào `AuthController`, và `AuthService.verifyOtp` cập nhật `status: 'active'` rồi trả cặp token mới (JWT payload phản ánh `active` ngay, không cần đăng nhập lại)
- [x] **Quyết định (đã đổi so với bản đầu):** *không* chặn login khi `pending_verification` — user vẫn đăng nhập bình thường, chỉ các route được đánh dấu `@RequireVerified()` (dùng `VerifiedGuard` có sẵn ở `verified.guard.ts`) mới trả 403. Đã nối demo route `GET /auth/verified-only` để minh hoạ pattern này — áp dụng lại cho các route nghiệp vụ thật (booking, upload...) khi các module đó được xây ở tuần sau
