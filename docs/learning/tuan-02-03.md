## Tuần 2

### Buổi 1 (~3h): Mongoose schema + đăng ký

**Học (1h):** Mongoose docs — Schema, Model, `@nestjs/mongoose` (`@Schema()`, `@Prop()`, `SchemaFactory`). bcrypt: salt là gì, cost factor (dùng 10–12), tại sao SHA256 không đủ cho mật khẩu (quá nhanh → brute-force dễ; bcrypt cố tình chậm).

**Làm (2h):**

- [ ] Tạo `users` schema theo [docs/04-data-model.md](../04-data-model.md): email/phone unique index, `password_hash`, `role`, `status` (mặc định `pending_verification`)
- [ ] `AuthModule` + `POST /auth/register`: DTO với `class-validator` (email hợp lệ, password ≥ 8 ký tự), hash bằng `bcrypt.hash(password, 10)`
- [ ] Lưu ý Q7: field `role` nên là **mảng roles** hoặc thiết kế cho phép một user giữ cả 2 vai trò — quyết định và ghi vào Nhật ký

**Tự vấn:** unique index của Mongo khác validate trong DTO thế nào? (index chặn race condition, DTO chỉ chặn input xấu — cần cả hai). Email trùng thì API trả lỗi gì — 409 hay 400?

### Buổi 2 (~3h): JWT login — access token

**Học (1h):** cấu trúc JWT (header.payload.signature), jwt.io để decode thử. Access vs refresh: access ngắn hạn (15') đi kèm mọi request, refresh dài hạn (7 ngày) chỉ dùng để xin access mới. Lưu ở đâu: cookie httpOnly (chống XSS đọc trộm) vs localStorage (đơn giản nhưng XSS đọc được) — chọn 1, ghi trade-off vào Nhật ký.

**Làm (2h):**

- [ ] `POST /auth/login`: so mật khẩu bằng `bcrypt.compare`, sai trả 401 với **thông báo chung chung** ("email hoặc mật khẩu sai" — không lộ email tồn tại hay không)
- [ ] Ký access token bằng `@nestjs/jwt`, payload tối thiểu: `sub` (user id), `roles`, hết hạn 15 phút
- [ ] Passport JWT strategy + `JwtAuthGuard`; endpoint thử `GET /auth/me` trả thông tin user hiện tại

### Buổi 3 (~3h): Guard, decorator, phân quyền

**Học (45'):** NestJS docs — Guards, Custom decorators, `Reflector` + `SetMetadata`.

**Làm (2h15'):**

- [ ] Custom decorator `@CurrentUser()` lấy user từ `request.user`
- [ ] `@Roles('photographer')` + `RolesGuard`: đọc metadata bằng `Reflector`, so với roles trong token
- [ ] Test bằng curl: user chỉ có role customer gọi endpoint photographer → 403

**Tự vấn:** Guard chạy trước hay sau Pipe/Interceptor? (thứ tự: Middleware → Guard → Interceptor → Pipe → Handler). `JwtAuthGuard` và `RolesGuard` phối hợp thế nào khi gắn cả hai?

### Buổi 4 (~3h): Refresh token + rotation + revoke qua Redis

Phần khó nhất module — làm chậm và vẽ diagram trước khi code.

**Học (45'):** tại sao cần rotation: nếu refresh token bị lộ, rotation làm token cũ vô hiệu ngay lần dùng kế tiếp → phát hiện được trộm. Đọc về "refresh token reuse detection".

**Làm (2h15'):**

- [ ] Login trả thêm refresh token (7 ngày), lưu **hash** của nó vào Redis với key `refresh:{userId}:{tokenId}`, TTL 7 ngày
- [ ] `POST /auth/refresh`: verify refresh token → so với Redis → cấp cặp token **mới**, xoá key cũ (rotation)
- [ ] `POST /auth/logout`: xoá refresh token khỏi Redis → token cũ bị từ chối
- [ ] Dùng lại refresh token đã rotate → 401 (và cân nhắc: revoke toàn bộ session của user đó)

**✅ Kiểm chứng giữa module:** vẽ sequence diagram luồng refresh **không nhìn tài liệu** — Customer → API → Redis, đủ 3 tình huống: access hết hạn, refresh hợp lệ, refresh đã bị rotate.

Phần này bạn có lợi thế FE — mục tiêu là **tự viết lại pattern interceptor từ đầu** thay vì copy từ dự án cũ.

**Làm:**

- [ ] Form đăng ký/đăng nhập bằng MUI + react-hook-form, validate khớp DTO phía server

```bash

# 3. retry /me với token mới → 200
# 4. logout → gọi /auth/refresh bằng token cũ → 401
```
